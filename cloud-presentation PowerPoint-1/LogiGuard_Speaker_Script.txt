LOGIGUARD AI: 10-MINUTE PRESENTATION SCRIPT
============================================================

============================================================
SLIDE 1: LOGIGUARD AI (TITLE SLIDE)   (about 0:20)
============================================================

Hello everyone. My name is Elham, and today I will present LogiGuard AI.

LogiGuard is an AI application. 
It predicts which orders are at risk of late delivery, 
and it helps logistics operators decide which shipments they should check first.


============================================================
SLIDE 2: THE BUSINESS PROBLEM   (about 0:45)
============================================================

Let me start with the problem.

Imagine a logistics operations coordinator. 
Every day, they are responsible for many shipments at the same time. 
Most of them are fine, but some will arrive late.

Today, orders are often checked by hand, 
and many times the problem is only noticed when the delay has already happened. 
And the information they need is spread across different places.

So the key question is: which shipments are most likely to be late, 
and which ones should I investigate first?


============================================================
SLIDE 3: THE SOLUTION: AI-POWERED DECISION SUPPORT   (about 0:50)
============================================================

My solution is a decision-support system. It works in five steps.

A new order comes in, through the API or the dashboard. 
An XGBoost model calculates the probability that this order will be late. 
All orders are shown in a queue, sorted from highest to lowest risk, 
with four simple levels: no risk, low, medium and high risk.

When the operator wants to understand an order, they ask the AI Copilot, 
which collects evidence and explains it. And finally, the human makes the decision.

To be clear: this is not a route optimizer, and it never acts on its own.


============================================================
SLIDE 4: FROM RAW DATA TO A CLEAN TRAINING SET   (about 0:50)
============================================================

Now the data. I used the public DataCo supply-chain dataset, 
with about 180,000 rows and 53 columns. Each row is one product item inside an order.

My pipeline first validates and cleans the data. 
Then it combines all items of an order into one row, 
because the business decision is made for the whole order. 
This gives 65,752 orders. 
It also makes sure that items from the same order cannot end up in both training and test data.

The target is binary: late or not late. 
About 55 percent are late, so the classes are reasonably balanced. 
The model uses 14 features


============================================================
SLIDE 5: PREVENTING DATA LEAKAGE: AN HONEST EVALUATION   (about 0:50)
============================================================

A very important part of this project was preventing data leakage. 
Leakage means the model sees information it would not have in real life, 
so the results look better than they really are.

First, I split the data by time, not randomly. 
The oldest 70 percent of orders are for training, 
the next 15 percent for validation, 
and the newest 15 percent for testing. 
This simulates predicting the future.

Second, I removed future information, 
like the real shipping days and the delivery status. 
These are only known after shipping.

Third, all preprocessing is learned only on the training data. 
And the test set was used only once, at the very end.


============================================================
SLIDE 6: MODEL SELECTION: FOUR MODELS COMPARED   (about 0:50)
============================================================

Next, I compared four models on the validation set. 
Logistic Regression was my baseline, with a ROC-AUC of 0.743.

The first versions of the Decision Tree and the Random Forest overfitted: 
they scored a perfect 1.0 on the training data. So I tuned all the tree models.

After tuning, the three tree models were close. 
I chose XGBoost because it had the highest ROC-AUC, 0.772, 
the best recall, less overfitting than the Random Forest, 
and it trains in under a third of a second.

To be honest, the difference is small, so this was a careful trade-off, not a big win.


============================================================
SLIDE 7: CHOOSING THE THRESHOLD AND THE FINAL TEST   (about 0:55)
============================================================

The model gives a probability, and a threshold decides when we call an order "late".

The default is 0.5. But here, missing a late order is worse than checking one extra order. 
So, using only validation data, 
I lowered the threshold to 0.40. 
As the chart shows, missed late orders dropped from about 2,200 to about 1,300. 
The cost is more false alarms, which is acceptable because a human reviews every alert.

Then I evaluated the model once on the untouched test set. 
Recall is 84 percent, precision 64 percent, and ROC-AUC 0.775. 
So the model caught 4,563 late orders and missed 867.

These are results on historical data, not measured production accuracy.


============================================================
SLIDE 8: SYSTEM ARCHITECTURE   (about 0:50)
============================================================

This is the system architecture. Everything runs with Docker Compose as five services.

The operator uses a Streamlit interface, with a risk dashboard, order details,
a form for new orders, and the Copilot.

The interface talks to a FastAPI service. 
The API loads the approved XGBoost model, 
makes predictions, and runs the Copilot.

All data is stored in PostgreSQL: the raw order, 
the processed order, and the prediction. 
Each prediction also stores the model version and threshold, so every result is traceable.

Prometheus collects the API metrics, and Grafana shows them on a dashboard. 
One command starts the whole system.


============================================================
SLIDE 9: OPERATIONS COPILOT: GROUNDED AND READ-ONLY   (about 0:55)
============================================================

Now the Operations Copilot, the AI agent of this project. I designed it to be safe and limited.

The operator chooses an order and an action. 
Each action calls exactly one approved tool, 
and all three tools only read from the database: get the prediction, get the shipment, 
or find similar shipments.

Then a validator checks the evidence, 
for example that the probability is a number between zero and one. 
Only after that, Google Gemini writes a short answer in plain language.

The important point: the XGBoost model makes the prediction, 
not the language model. Gemini must use only the evidence and cannot change any numbers. 
If Gemini is unavailable, the checked evidence is still shown. 
And the Copilot can never change data or take actions.


============================================================
SLIDE 10: MODEL LIFECYCLE: FROM TRAINING TO PRODUCTION, SAFELY   (about 0:45)
============================================================

A production-style system also needs a safe model lifecycle.

Every time I prepare data or train a model, a new versioned copy is created. 
But a new model never goes live automatically. It must pass a quality gate, 
a validation ROC-AUC of at least 0.75, and then a person must promote it manually.

For versioning, Git tracks the code, DVC tracks the exact dataset, and MLflow records the model settings and results. So every part is traceable.


============================================================
SLIDE 11: MONITORING AND QUALITY ASSURANCE   (about 0:45)
============================================================

For monitoring, Prometheus and Grafana show traffic, errors, 
latency and memory, and an alert fires if the API is down for one minute. 
Evidently compares new data with the training data. If there are fewer than 30 new orders, 
the report honestly says "insufficient data".

For quality, I have 33 automated tests, and all of them pass. 
Ruff checks the code quality. And on every push, GitHub Actions installs the project, 
checks the code, runs the tests on a separate test database, and builds the Docker image.


============================================================
SLIDE 12: LIMITATIONS AND NEXT STEPS   (about 0:35)
============================================================

Of course, there are limitations. The model was trained on historical public data, 
not on a real company's live shipments. Without real delivery outcomes, 
I cannot measure production accuracy. Data and experiment history are stored locally, 
and monitoring is still partly manual.

My next steps would be: validate with real company data, 
collect real outcomes, add shared storage, and automate monitoring and alerts.


============================================================

============================================================

To summarize: LogiGuard turns historical data into a risk-ranked and explainable shipment queue, and the human always stays in control.

Thank you very much. I am happy to answer your questions.

============================================================
POSSIBLE QUESTIONS AND SHORT ANSWERS
============================================================

Q1: Why did you aggregate the data to order level?

A: The business decision is made for one order, not for one item. One order can have up to five items. If I trained on items, the same order could appear in both training and test data. That would be leakage.

Q2: What is data leakage, and how did you prevent it?

A: Leakage means using information that is not available at prediction time. I removed after-shipping columns like the real shipping days and the delivery status, I split the data by time, and I fitted all preprocessing on the training data only.

Q3: Why did you choose XGBoost?

A: It had the highest validation ROC-AUC (0.772), the best recall, a smaller overfitting gap than Random Forest, and it is fast. The tuned tree models were close, so it was a careful trade-off.

Q4: Why a threshold of 0.40 and not 0.50?

A: Missing a late order is worse than checking an extra one. At 0.40, validation recall went from 59% to 76%. We get more false alarms, but a human reviews every alert. The threshold was chosen on validation data only.

Q5: What do recall and precision mean here?

A: Recall 84%: the model found 84 out of 100 truly late orders in the test data. Precision 64%: of the orders it flagged as late, 64 out of 100 were really late.

Q6: What does ROC-AUC mean?
A: It measures how well the model ranks risky orders above safe ones, across all thresholds. 0.5 is random guessing, 1.0 is perfect. Our test ROC-AUC is 0.775.

Q7: Is Gemini making the prediction?
A: No. XGBoost makes the prediction. Gemini only explains evidence that was already checked by the validator. If Gemini fails, the structured evidence is still returned.

Q8: What can the Copilot do, and what can it not do?
A: It has three read-only tools: get prediction, get shipment, and find similar shipments. It cannot change data, contact carriers, book transport or change routes.

Q9: Can a newly trained model go live automatically?
A: No. Training only creates a new candidate. A person must run a separate promotion step, which checks that validation ROC-AUC is at least 0.75.

Q10: Why do you use both DVC and MLflow?
A: They answer different questions. DVC says which dataset version was used. MLflow records the model settings and results. Git versions the code.

Q11: How do you monitor the system?
A: Prometheus and Grafana monitor the API: traffic, errors, latency, memory, plus an API-down alert. Evidently compares new data with the training data. But drift is not accuracy; for accuracy we need real delivery outcomes.

Q12: How do you know your code works?
A: 33 automated tests pass, Ruff checks code quality, and GitHub Actions runs linting, tests on a PostgreSQL test database, and a Docker build on every push and pull request.

Q13: How many containers are there?
A: Five Docker Compose services: PostgreSQL, the FastAPI API, the Streamlit UI, Prometheus and Grafana.

Q14: Why is order_hour a feature, is it leakage?
A: It is known when the order is created, so it is not classic leakage. But in this dataset it is related to how the target was calculated for Same Day orders. Removing it lowered ROC-AUC from 0.772 to 0.739, so I kept it and documented it as a limitation.

Q15: What would you improve next?
A: Collect real delivery outcomes to measure true performance, add shared storage for data and experiments, add alert notifications and scheduled drift checks, and validate on real company data.
